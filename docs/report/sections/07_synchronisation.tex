% ============================================================================
\section{Synchronisation and Reliability}
\label{sec:sync}
% ============================================================================

Several tasks run at the same time and some resources are shared, so \req{2.7} is met with a small
set of rules, each tied to a specific risk.

\subsection{Design rules}
\begin{enumerate}
  \item \textbf{One writer per record.} Only the hub task decides access and changes the occupancy
        ledger; card scans from any source are \emph{queued} to it and processed one at a time.
        Two people scanning at once can never produce an inconsistent ledger.
  \item \textbf{One owner per device.} Only the storage task touches the SD card, and only the ui
        task touches the LCD. Other tasks send requests through queues.
  \item \textbf{One mutex per shared module.} Users, config, occupancy, auth, the light-sensor ADC
        and the hub status each have their own lock, held only for a quick copy. Readers (CLI, LCD)
        get a copy, never a pointer into live data.
  \item \textbf{Interrupts never block.} They only queue an event or notify a task.
\end{enumerate}

\subsection{Coordination between terminals}
The terminals coordinate only through bus messages (\cref{sec:sw-bus}). A room never waits for the
hub: if a send fails, the room keeps its lights correct and tries again with the next report. The
hub never waits for a room either; it uses the latest state each room reported and marks a room
offline when its heartbeats stop. This is the same failure model that three separate boards would
have.
