\subsection{Simulation testing in Wokwi}
The system is tested in the Wokwi simulator in two ways: interactively in VS Code, and
automatically with the Wokwi CLI, which runs the real firmware image against
\file{firmware/diagram.json} and follows a YAML scenario. A scenario presents the reader's
preset cards, sets the light sensors, types console commands, and fails unless each expected
line appears on the serial port:
\begin{lstlisting}[style=console]
wokwi-cli firmware --scenario test/wokwi/access.test.yaml --timeout 60000
wokwi-cli firmware --scenario test/wokwi/demo.test.yaml   --timeout 90000
wokwi-cli firmware --scenario test/wokwi/rules.test.yaml  --timeout 120000
\end{lstlisting}
\code{make sim} runs all three. All three pass. The online project (\wokwilink) was also
built by wokwi.com's ESP-IDF~v5.3 builder and run: it boots, logs card scans at the entry reader,
and reports daylight changes, as the local build does. The console figures in \cref{sec:operation} are their captured output.

\subsection{Defects found and fixed}
Testing in the simulator and code review found real bugs, which were fixed:
\begin{itemize}
  \item \textbf{Crash loop when a lamp faded on.} The ESP32's hardware LED-fade interrupt fired
        endlessly in Wokwi and tripped the interrupt watchdog. Because a software reset does not
        clear that peripheral, every reboot crashed again. The backtrace pointed to
        \code{ledc_fade_isr}; we removed the hardware fade and fade the lamp in software from the
        room task instead.
  \item \textbf{Bus ordering race} (\cref{sec:sync}): fixed with a per-sender mutex.
  \item \textbf{PIN format}: PINs are exactly 4 digits, checked when a PIN is set and when it is
        typed.
  \item \textbf{LCD overflow}: every row is now formatted to exactly 20 characters.
  \item \textbf{Late PIN after a timeout} was accepted by mistake; the state machine now checks
        expiry first, and a unit test covers it.
\end{itemize}

\subsection{Dashboard}
\code{prisma validate}, the TypeScript check and \code{next build} pass. The initial migration
was applied to the Neon database with \code{prisma migrate deploy}, and replaying the migrations
into a throwaway Docker Postgres matches the schema exactly. With the production build running
against Neon, the sample sender inserted 18 events, then 18 duplicates on a second run
(idempotent); a bad signature and a stale timestamp were rejected with HTTP 401, and a signed but
malformed batch with HTTP 400. The overview, access-log and energy pages render the stored data
(\cref{fig:dashboard}). The same checks pass against the Vercel deployment: pages load from
Neon, a signed new event is stored, re-sent events count as duplicates, and tampered,
stale or malformed requests get 401 or 400.
